# Spec: Экраны тренировки таблицы умножения (Умножение на 1…9)

Date: 2026-10-24
Status: approved
Slug: multiplication-screens

---

## Context and Motivation

Приложение `Math.py` — настольный тренажёр устного счёта на tkinter с девятью экранами упражнений
(сложение, вычитание, вычитание через десяток). Таблица умножения в нём не покрыта вообще.

Фича добавляет тренировку таблицы умножения с разбивкой по фиксированному первому множителю: один
экран — один «столбик» таблицы, чтобы тренировать его без переключения контекста (первый множитель
в вопросе не меняется всё время, пока окно открыто). Полное покрытие всех восьми значений второго
множителя за сессию при этом **не гарантируется**: `b` выбирается случайно с запретом только
немедленного повтора — перемешанный цикл с гарантированным покрытием пользователь отверг осознанно
(см. §Decisions Made).

На главном экране появляется четвёртый столбец из девяти кнопок «Умножение на 1» … «Умножение на 9»;
каждая открывает экран, где фиксированный множитель `a` умножается на случайное `b` из 2..9.
Механика, визуал и тайминги — те же, что у существующих экранов: ребёнок не должен переучиваться
под новый экран.

Выгода: закрывается последний большой пробел в наборе упражнений, причём без новых зависимостей и
без изменения существующих экранов — работа аддитивна.

## Acceptance Criteria

Фича завершена, когда истинно ВСЁ перечисленное.

### Контур верификации (три слоя, владельцы разные)

| Слой | Чем закрывается | Владелец |
|---|---|---|
| V1 — структурный headless-скрипт | `/usr/bin/python3`, `import Math`, инстанцирование `MathTrainer` и `MultiplicationScreen` в шелле без дисплея; чтение `grid_info()`, `cget(...)`, `winfo_req*()`, `title()`, `geometry()`; подача ответа через `button.invoke()`, прямые вызовы `reset_stats()`, `go_back()`, `finish_turn()`; прокрутка таймеров через `root.after(2200, root.quit)` + `mainloop()` | Agent |
| V2 — скрипт инварианта генератора | Тот же `import Math`; скрипт **инстанцирует реальный `MultiplicationScreen` на headless `Toplevel`** (V1 доказывает, что это работает) и вызывает на экземпляре `screen.pick_second_multiplier()` и `screen.build_answer_options(a, b)` — **поставляемый код, не реимплементацию**. Оба метода — обычные методы экземпляра с `self`; `@staticmethod` не применять: в `Math.py` ноль декораторов (проверено), это сломало бы требование воспроизводить стиль | Agent |
| V3 — L5, наблюдение GUI | Ручной прогон окна: цвета, читаемость, ощущение паузы, отсутствие визуальных артефактов | **Human** |

**Интерпретатор приёмки зафиксирован: `/usr/bin/python3`** (Python 3.9.6, Tk 8.5 — проверено
запуском). `python` на PATH отсутствует; `python3` из Homebrew падает
`ModuleNotFoundError: No module named '_tkinter'`. Поскольку `import tkinter as tk` стоит на уровне
модуля (`Math.py:2`, вне `try`), неверный интерпретатор даёт traceback, а не сообщение из
`Math.py:1427-1428`. Все команды запуска в этой спеке — `/usr/bin/python3 Math.py`. Целевая версия
Tk — **8.5**; пиксельные сличения на Tk 8.6 могут расходиться и в приёмке не используются.

**Два механических факта про V1, без которых скрипт даёт ложные результаты (проверено запуском):**
`import Math` безопасен — `mainloop()` закрыт блоком `if __name__ == "__main__"` (`Math.py:1422`);
перед чтением любой геометрии нужен `root.update_idletasks()` — без него `frame.winfo_reqwidth()`
возвращает `1`.

V1 и V2 — одноразовые скрипты: в репозиторий не коммитятся (см. §Affected Modules), но их текст и
дословный вывод фиксируются в квитанции (AC-8).

### Критерии

- [ ] **AC-1** — На главном экране присутствуют девять кнопок с текстами `Умножение на 1`,

  `row=N`), оформление как у остальных кнопок сетки: `font=("Arial", 18)`, `width=20`, `height=2`,
  `grid(..., padx=10, pady=5)` (канон — `Math.py:31-32, 46-50`). Девятая кнопка попадает в экран
  без прокрутки на минимальном целевом разрешении **1024×768**.

  `cget('font') == 'Arial 18'`, `cget('width') == 20`, `cget('height') == 2`, `grid_info()['padx'] == '10'`,
  `grid_info()['pady'] == '5'`, `winfo_reqwidth() == 228`, `winfo_reqheight() == 54`; после
  `root.update_idletasks()` — `root.winfo_reqwidth() <= 1024` и `root.winfo_reqheight() <= 768`
  (замеры до правки: кнопка 228×54, ячейка с отступами 248×64, `frame` 744×640, `root` 744×694,
  ожидание после добавления столбца ≈ 992×694). Машинный ассерт сравнивает требуемую геометрию с
  НОМИНАЛЬНЫМ разрешением и не учитывает строку заголовка окна, menu bar и Dock, а запас по высоте
  ~20 px — поэтому он необходим, но не достаточен.
  *V3 (обязательный шаг, не наблюдение «на глаз»):* наблюдатель подтверждает, что кнопка
  `Умножение на 9` видна целиком и нажимаема на экране 1024×768 с обычными системными панелями.
  *V3:* визуальный контроль четвёртого столбца и порядка номеров. Прокрутки у дашборда нет и не
  будет (см. §Out of Scope); `self.root.state('zoomed')` (`Math.py:12`) на macOS исключения не
  бросает, но окно остаётся в состоянии `normal` — развёрнутого окна реализатору ждать не нужно.

- [ ] **AC-5** — Текст вопроса имеет вид `f"{a} × {b} = ?"` (знак `×`, U+00D7), где `a` — номер
  экрана, зафиксированный на всё время жизни окна, `b` — целое из 2..9.
  *V1:* 1000 итераций `generate_question()` + `next_question()`: регулярным выражением разобрать
  `question_label.cget('text')`, проверить, что левый множитель всегда равен `multiplier`, правый
  всегда в 2..9, формат совпадает дословно. *V3:* прогон 30 вопросов глазами.
- [ ] **AC-6** — Второй множитель `b` нового вопроса никогда не равен `b` предыдущего вопроса на том
  же экране.
  *Первичный верификатор — структурная проверка кода:* `pick_second_multiplier()` выбирает значение
  из набора, из которого `previous_b` исключён ДО выбора (`random.choice` по отфильтрованному
  списку), цикла перевыбора и ограничителя попыток нет. *V2:* по СВЕЖЕМУ экземпляру экрана — 1000
  последовательных вызовов `screen.pick_second_multiplier()`: ни одной пары одинаковых значений
  подряд, все 8 значений встречаются. Повторный прогон требует нового экземпляра (или явного
  `previous_b = None`): метод мутирует `self.previous_b` и значение `a` вообще не читает, поэтому
  «прогон для каждого `a`» смысла не имеет. *V3:* 30
  вопросов глазами — вторичное подтверждение (выборка абсолютное утверждение доказать не может,
  доказывает его структура кода).
- [ ] **AC-7** — На шести кнопках вариантов всегда показаны шесть РАЗЛИЧНЫХ строго положительных
  целых; правильный ответ `a*b` всегда среди них; `0` и отрицательные значения не показываются
  никогда; пустых кнопок (`text=""` после `next_question()`) нет.
  *V2:* `screen.build_answer_options(a, b)` по всем 432 комбинациям (`a` 1..9 × `b` 2..9 × 6
  вариантов отброшенной формулы) — ноль нарушений.
  *V1 — обязательный ассерт согласованности вопроса и кнопок (без него рассинхрон проходит контур
  зелёным):* после каждого из 100 вызовов `next_question()` на экране `a=1` и ещё 100 на `a=7`
  разобрать текст `question_label`, вычислить `a*b` из разобранных множителей и проверить, что
  (1) `screen.correct_answer == a*b`; (2) ровно ОДНА из шести кнопок имеет
  `cget('text') == str(screen.correct_answer)`; (3) все шесть текстов непусты, различны, приводятся
  к целому `> 0`. Затем `invoke()` именно найденной кнопки и проверка `result_label.cget('text') ==
  "Correct! Well done!"` — то есть правильность кнопки доказывается через живой экран, а не
  сравнением `correct_answer` с самим собой.
- [ ] **AC-8** — Инвариант генератора подтверждён и задокументирован. Прогон V2 по 432 комбинациям
  печатает: `432` проверенных комбинации, `0` нарушений, `96` комбинаций с добором из резерва,
  максимальная глубина добора `3`, распределение глубин `336 / 32 / 56 / 8` (0 / 1 / 2 / 3 добора).
  **Совпадение распределения `336/32/56/8` корректность шага 4 НЕ доказывает:** распределение
  глубин определяется фильтрами шага 3 и к порядку сканирования резерва слепо (проверено: у двух
  разных прочтений шага 4 оно идентично).
  **Обязательные эталонные наборы** (индексация `drop` — по порядку формул §Technical Approach,
  шаг 2; сверяются как МНОЖЕСТВА, порядок после `random.shuffle` произволен). Все восемь ассертов
  обязательны, ни один не опциональный:

  | Комбинация | Ожидаемый набор | Роль |
  |---|---|---|
  | `a=1, b=2`, каждый `drop ∈ {0..5}` | `{1,2,3,4,5,6}` | базовый; к порядку сканирования резерва **слеп** |
  | `a=3, b=3`, `drop ∈ {0,1,2,3}` | `{6,8,9,10,11,12}` | базовый |
  | `a=9, b=9`, `drop ∈ {0,1,2,3}` | `{72,80,81,82,83,90}` | базовый |
  | **`a=3, b=3`, `drop = 4`** | **`{6,7,9,10,11,12}`** | **различающий**: неправильное прочтение шага 4 даёт `{6,9,10,11,12,13}` |
  | **`a=3, b=3`, `drop = 5`** | **`{6,7,8,9,11,12}`** | **различающий**: неправильное прочтение даёт `{6,8,9,11,12,13}` |

  Два последних — единственные эталоны, различающие плоское сканирование резерва и ошибочное
  прочтение «не более одного кандидата на шаг `k`» (расходятся в 58 комбинациях из 432, при этом
  ОБА прочтения удовлетворяют AC-7 во всех 432 — проверено прогоном). Без них самая естественная
  неправильная реализация шага 4 проходит приёмку.
  **Как V2 форсирует `drop`** (без этого исчерпывающий перебор невозможен — `drop` выбирается
  внутри `build_answer_options`): скрипт подменяет `Math.random.randrange` на функцию, возвращающую
  нужный индекс, и восстанавливает исходную после прогона. Канал проверен запуском:
  `Math.random is random` → `True`, подмена видна внутри модуля; `random.shuffle` модульный
  `randrange` не вызывает, поэтому подмена не искажает перемешивание. Сигнатуру поставляемого кода
  менять под тесты нельзя — тестового параметра `drop` в `build_answer_options` быть не должно.
  **Ассерт против молчаливого no-op (обязателен):** подменённая функция считает свои вызовы, и
  скрипт проверяет `число вызовов == число вызовов build_answer_options` (432 при полном прогоне:
  9 значений `a` × 8 значений `b` × 6 вариантов `drop`). Если реализация взяла
  `random.randint`/`random.choice` вместо `random.randrange`,
  счётчик останется нулевым, и исчерпывающий перебор не выродится молча в 432 случайные выборки.
  Скрипт запускается из корня репозитория, иначе `import Math` не резолвится.
  **Квитанция обязательна:** текст скрипта V2 и его дословный вывод записываются в
  `swarm-report/multiplication-screens-invariant-receipt.md`, иначе после удаления скрипта инвариант
  невоспроизводим.

## Technical Approach

### Класс экрана

`MultiplicationScreen(root, multiplier)` — структура `NoBorrowSubtractionScreen`
(`Math.py:1283-1418`, новейший стабилизированный паттерн) плюс кнопка сброса из старого паттерна и
плюс два новых элемента: выделенные методы генерации, не обращающиеся к виджетам, и учёт
отложенного вызова `after`. Все методы — обычные методы экземпляра с `self`; `@staticmethod` и любые
декораторы не применять (в `Math.py` ноль декораторов). Состав методов фиксирован:

| Метод | Ответственность | Обращение к виджетам |
|---|---|---|
| `__init__(self, root, multiplier)` | Собрать UI (AC-4), инициализировать состояние, вызвать `self.next_question()` | да |
| `go_back(self)` | `self.cancel_pending()`, затем `self.root.destroy()` | да |
| `cancel_pending(self)` | Если `self.pending_after` непуст — `self.root.after_cancel(...)` и `self.pending_after = None` | да (только `after_cancel`) |
| `reset_stats(self)` | Обнулить оба счётчика, `self.pending_counts = False`, `update_stats()`. Поток вопросов НЕ трогает: ни `after_cancel`, ни `next_question` здесь нет | да |
| `pick_second_multiplier(self)` | Вернуть `b` из 2..9, исключив `self.previous_b`, и присвоить `self.previous_b = b` | **нет**; мутирует только `self.previous_b` |
| `build_answer_options(self, a, b)` | Вычислить `correct = a * b` внутри и вернуть список ровно из 6 значений (шаги 2-5 алгоритма) | **нет**; ни виджетов, ни состояния экрана |
| `generate_question(self)` | `self.num1 = self.multiplier`, `self.num2 = self.pick_second_multiplier()`, `self.correct_answer = self.num1 * self.num2` | нет |
| `next_question(self)` | `generate_question()`, обновить текст вопроса, очистить `result_label`, получить список из `self.build_answer_options(self.num1, self.num2)` и раздать по кнопкам с `state='normal'` | да |
| `check_answer(self, selected_answer)` | Заблокировать все шесть кнопок, вывести результат, `self.pending_counts = True`, `self.pending_after = self.root.after(2000, lambda: self.finish_turn(<bool>))` | да |
| `finish_turn(self, was_correct)` | `self.pending_after = None`; инкремент счётчика ТОЛЬКО если `self.pending_counts`; затем `self.pending_counts = False`, `update_stats()`, `next_question()` | да |
| `update_stats(self)` | Переписать текст обоих labels статистики | да |

Выделение `pick_second_multiplier` и `build_answer_options` — требование верифицируемости: без них
единственным способом проверить арифметику остаётся вторая реализация алгоритма в скрипте, то есть
проверка не поставляемого кода. Новых файлов, модулей, импортов и зависимостей это не вводит, то
есть запрету из §Out of Scope («выделение генератора в тестируемый модуль») не противоречит.
`correct` в `build_answer_options` параметром НЕ передаётся: он вычисляется из `a` и `b` внутри,
поэтому согласованность вопроса и набора вариантов структурная, а не проверяемая тестом.
V2 получает оба метода, инстанцируя реальный `MultiplicationScreen` на headless `Toplevel` и вызывая
их на экземпляре.

Состояние экрана: `self.root`, `self.multiplier`, `self.num1`, `self.num2`, `self.correct_answer`,
`self.answers`, `self.correct_count`, `self.incorrect_count`, `self.previous_b` (инициализируется
`None`), `self.pending_after` (инициализируется `None`), `self.pending_counts` (инициализируется
`False`), `self.option_buttons` (список из 6) и ссылки на виджеты с именами из таблицы AC-4.

`self.num1` присваивается в `generate_question()` при КАЖДОМ вопросе (как в образце
`Math.py:1364-1365`), а не однократно в `__init__`; значение всегда равно `self.multiplier`.

Заголовок окна — `f"Умножение на {multiplier}"` (совпадает с текстом кнопки). Текст вопроса —
`f"{self.num1} × {self.num2} = ?"`, знак `×` (U+00D7), не `*` и не `x`.

### Алгоритм генерации вариантов (переносить пошагово и полностью)

Обозначения: `a` — номер экрана (`multiplier`, 1..9), `b` — второй множитель.

1. **Выбор `b` и правильный ответ.** `b` выбирается равновероятно из множества `{2..9} \ {previous_b}`
   — то есть выбор идёт по УЖЕ отфильтрованному набору (`random.choice` по списку-comprehension),
   цикла перевыбора и ограничителя попыток здесь НЕТ. После выбора `previous_b = b`.
   `correct = a * b`. Обязательный комментарий в коде, дословно:
   `# previous_b исключён до выбора, поэтому перевыбора в цикле не нужно`
2. **Шесть формул дистракторов**, индексация 0..5 именно в этом порядке:
   `0: (a-1)*b`, `1: (a+1)*b`, `2: a*(b-1)`, `3: a*(b+1)`, `4: a*b-1`, `5: a*b+1`.
   **Одна из шести отбрасывается случайно на каждом вопросе:** индекс `drop = random.randrange(6)`,
   остальные пять берутся list comprehension'ом с сохранением порядка индексов. **`random.randrange`
   здесь несущая деталь, заменять её на `random.randint(0, 5)` или `random.choice` нельзя**, хотя
   стиль файла тянет к `randint` (32 вхождения `random.randint`, 5 `random.choice`, 0
   `random.randrange` — проверено): V2 форсирует `drop` подменой именно `randrange`, и при другой
   функции исчерпывающий перебор молча выродится в 432 случайные выборки (ассерт-счётчик в AC-8
   делает такую подмену видимой). Первый множитель в
   дистракторах намеренно «плавает» (`(a-1)*b`, `(a+1)*b`): дистракторы берутся из соседних строк
   таблицы умножения, фиксирован `a` только в тексте вопроса. Обязательный комментарий в коде,
   дословно: `# первый множитель в дистракторах плавает намеренно: это соседние строки таблицы`
3. **Фильтры, строго в этом порядке.** Пять оставшихся значений просматриваются по порядку индексов;
   значение отбрасывается, если оно равно `correct`, равно `0`, либо уже попало в набор. Уцелевшие
   сохраняют относительный порядок.
4. **Добор из резерва — ОДНА плоская последовательность, сканируемая по порядку.** Резерв задаётся
   как единая упорядоченная последовательность ближайших целых к правильному ответу:
   `correct+2`, `correct-2`, `correct+3`, `correct-3`, `correct+4`, `correct-4`, … (`correct+k`,
   `correct-k` для `k = 2, 3, …, 50`). Пока в наборе меньше пяти значений, брать следующий элемент
   последовательности, проходящий фильтры: не равно `correct`, строго больше `0`, не дубликат.
   **Требование, различающее правильную и ошибочную реализацию:** после взятия кандидата следующий
   добор продолжает сканировать ТУ ЖЕ последовательность с места остановки и не перескакивает через
   непробованные значения. Ошибочное прочтение «не более одного кандидата на шаг `k`» (взял
   `correct+2` → `k` сразу уходит на 3, `correct-2` не пробуется вовсе) даёт другие наборы в 58
   комбинациях из 432, при этом тоже удовлетворяет AC-7 во всех 432 и даёт то же распределение
   глубин — ловится только двумя различающими эталонами AC-8.
   Цикл добора — единственный `while` в генераторе; ограничитель `k > 50` — страховка от
   бесконечного цикла. При домене `a ∈ 1..9`, `b ∈ 2..9` ограничитель недостижим: максимальная
   фактическая глубина добора — 3. Ветка исчерпания резерва — **мёртвый код** и обязана
   сопровождаться комментарием, дословно:
   `# недостижимо при a 1..9 и b 2..9: максимальная фактическая глубина добора 3 (прогон 432 комбинаций)`
   Возврат набора меньше шести значений недопустим: пустая кнопка нарушила бы AC-7.
5. **Сборка.** Правильный ответ добавляется шестым значением, все шесть перемешиваются
   (`random.shuffle`) и возвращаются вызывающему. `next_question()` раздаёт их по кнопкам:
   `text=str(value)`, `command`, замыкающий своё значение параметром по умолчанию, `state='normal'`
   (образец — `Math.py:1386-1387`).

**Проверенный инвариант (сохранить).** Прогон по всем 432 комбинациям (9 значений `a` × 8 значений
`b` × 6 вариантов `drop`): всегда ровно 6 различных строго положительных значений, правильный ответ
всегда среди них, ни одной пустой кнопки и ни одного дубликата. Резерв шага 4 задействуется в 96
комбинациях из 432 (распределение глубин: 336 без добора, 32 с одним, 56 с двумя, 8 с тремя),
максимальная глубина — 3; худший случай — экран «Умножение на 1». Любое отклонение от порядка шагов
2-4 инвариант может сломать: реализация обязана воспроизвести порядок, а V2 — подтвердить числа
заново и записать их в квитанцию (AC-8).

Почему коллизии вообще возможны (проверено исчерпывающим перебором всех 15 пар формул на `a ∈ 1..9`,
`b ∈ 2..9`). Сталкиваются ровно четыре пары: `(a-1)*b == a*(b-1)` ⇔ `a == b`;
`(a+1)*b == a*(b+1)` ⇔ `a == b`; `a*(b-1) == a*b-1` ⇔ `a == 1`; `a*(b+1) == a*b+1` ⇔ `a == 1`. То
есть на квадратах (`b == a`, по одному вопросу на экранах `a=2..9`) коллидируют **две** пары, и на
экране «Умножение на 1» — тоже две (плюс там же `(a-1)*b = 0` запрещён фильтром нуля). Остальные
одиннадцать пар не сталкиваются ни при каких значениях из этих диапазонов. Ни одна из шести формул
не может совпасть с правильным ответом при этих диапазонах — фильтр «равно `correct`» нужен как
страховка и как фильтр для резерва.

### Поток данных одного хода

`next_question()` → `generate_question()` (→ `pick_second_multiplier()`) → `build_answer_options()` →
отрисовка вопроса и кнопок → клик → `check_answer()` (блокировка кнопок, вывод результата,
`pending_counts = True`, `pending_after = root.after(2000, …)`) → `finish_turn()` (сброс
`pending_after`, зачёт хода при `pending_counts`, `update_stats()`) → `next_question()`.

### Обработка ошибок

Внешних источников данных, I/O и сети нет. Единственный реальный источник отказа — **отложенные
действия `root.after`**, выполняющиеся через 2000 мс после ответа, когда состояние экрана уже
изменилось. В существующем коде защиты нет: 11 вызовов `root.after(` и ноль вхождений
`after_cancel` / `WM_DELETE_WINDOW` (проверено). Новый экран закрывает это так:

- `self.pending_after` хранит id последнего запланированного `finish_turn`; `finish_turn` сбрасывает
  его в `None`.
- **`Сбросить` в течение паузы разрешается флагом, а не отменой таймера.** `check_answer` ставит
  `self.pending_counts = True`, `reset_stats` ставит `False`, `finish_turn` инкрементирует счётчик
  только при `True`. Ход, по которому нажали `Сбросить`, не засчитывается, а поток вопросов идёт
  штатно: строка `Incorrect. The correct answer is: …` остаётся на экране до конца паузы (ребёнок
  читает её именно в этот момент), следующий вопрос приходит в обычном темпе, заблокированных
  навсегда кнопок не возникает, потому что штатное завершение хода продолжает работать.
  Без флага `Сбросить` в паузе давал бы счёт `1 : 0` вместо `0 : 0` (нарушение AC-12); отмена
  таймера вместо флага стирала бы читаемый ответ и перескакивала вопрос.
- `go_back` вызывает `cancel_pending()` перед `destroy()` — единственное место с `after_cancel`.
  Это защитная гигиена, а не единственная линия обороны: в tkinter таймер, зарегистрированный на
  самом Toplevel, удаляется вместе с ним, и отложенный `finish_turn` после `destroy()` не
  выполняется и ошибок не печатает (проверено запуском: при таймере на уничтоженном Toplevel
  колбэк не срабатывает и stderr пуст, тогда как тот же таймер на выжившем root даёт
  `TclError: invalid command name`). Обязательный комментарий в коде, дословно:
  `# after_cancel защитный: таймер Toplevel умирает вместе с окном, но полагаться на это не стоит`
- **Закрытие окна системной ✕** идёт мимо `go_back`, поэтому `after_cancel` при нём не срабатывает —
  и это безопасно по тому же проверенному механизму: таймер зарегистрирован на закрываемом Toplevel
  и умирает вместе с ним. Поэтому хэндлер `WM_DELETE_WINDOW` намеренно НЕ вводится: он добавил бы
  расхождение с девятью существующими экранами, не закрывая ни одного наблюдаемого отказа.
- Циклов без ограничителя в новом коде нет: выбор `b` цикла не имеет (шаг 1), цикл добора резерва
  несёт ограничитель `k > 50` (шаг 4).
- Никаких блокирующих ожиданий и `time.sleep` в UI-потоке: только `self.root.after(...)`.

Отдельного error-UI фича не вводит: отказов, видимых пользователю, в её домене не остаётся.

## Technical Constraints

Правила, от которых агент-реализатор не отклоняется:

- Весь поставляемый код живёт в единственном файле `Math.py`. Новых файлов, модулей и пакетов в
  поставке не создавать (транзиентные скрипты верификации V1/V2 — исключение, см. §Affected Modules).
- Только стандартная библиотека и встроенный tkinter. **Новых зависимостей не добавлять**;
  `requirements.txt` не создавать.
- **Стиль кода проекта** (воспроизводить дословно): отступ **1 пробел** перед `def` внутри класса
  (так во всех 67 определениях файла); тело метода — **5 пробелов** на первом уровне и **+4 на
  каждый уровень вложенности** (5, 9, 13, 17), строки-продолжения выравниваются по открытой скобке;
  ровно **3 пустые строки** между методами; без docstring и без type hints. Исключение, которое НЕ копировать:
  `AdditionScreen` содержит нерегулярные отступы в теле `generate_question_via` (3 и 6 пробелов,
  `Math.py:380-393`).
- Комментарии: четыре обязательных комментария с дословным текстом заданы в §Technical Approach
  (выбор `b`, плавающий первый множитель, мёртвая ветка резерва, защитный `after_cancel`). Это
  места, где код выглядит неправильным, но верен, — комментарий обязателен.
- UI-строки: служебные по-английски дословно как в каноне (`Back`, `Correct! Well done!`,
  `Incorrect. The correct answer is: {…}`, `Correct: {n}`, `Incorrect: {n}`), новые пользовательские
  строки по-русски (`Умножение на N`, `Сбросить`).
- Канон UI менять нельзя: окно `500x700`, `bg='lightblue'`, шрифты, цвета и отступы из AC-4,
  оформление кнопок главной сетки из AC-1.
- Новый паттерн экрана обязателен: 6 кнопок вариантов в сетке `row=i//3, column=i%3`, пауза
  `2000` мс, блокировка всех кнопок **до** вывода результата, завершение хода в отдельном
  `finish_turn(was_correct)`, два отдельных label статистики (зелёный/красный).
- Существующие девять классов экранов не изменять ни строкой.
- **Интерпретатор:** `/usr/bin/python3` (3.9.6, Tk 8.5). `python` отсутствует, `python3` из Homebrew
  без `_tkinter`. Запуск приложения — `/usr/bin/python3 Math.py`.
- Тестовой инфраструктуры в проекте нет (ни тестов, ни линтеров, ни CI, ни `requirements.txt`) и эта
  спека её не вводит. Автоматических уровней L0/L1a нет; базовая проверка синтаксиса — успешный
  `/usr/bin/python3 Math.py` и успешный `import Math`; машинная проверка поведения — транзиентные
  скрипты V1/V2 поверх поставляемого кода; наблюдение GUI — L5 человеком.

## Out of Scope

НЕ будет реализовано в рамках этой спеки:

- **Исправление бага перепутанных операндов в `NoBorrowSubtractionScreen` (`Math.py:1359-1373`).**
  Экран называется «Минус: 1-значное из 2-значного», но `self.correct_answer = num1 - num2`, где
  `num1` однозначное, а `num2` двузначное: вопрос выходит «3 - 47 = ?» с ответом -44 вместо
  «47 - 3 = ?». Выбор `units2 = random.randint(num1, 9)` с комментарием «no borrow across the tens
  digit» задуман для порядка `num2 - num1`, то есть исходный замысел подтверждает перестановку.
  **Прямое предупреждение реализатору:** этот класс — главный образец для нового экрана, слепое
  копирование его `generate_question`/`next_question` перенесло бы дефект в умножение. Копировать у
  него СТРУКТУРУ (UI, тайминги, блокировку, `finish_turn`), арифметику брать только из §Technical
  Approach. *Баг уже сейчас виден ребёнку — требуется отдельная задача (владелец: Human, цель:
  отдельная спека), не «когда-нибудь».*
- **Предсуществующая гонка отложенных `after` на девяти старых экранах** (`after_cancel` и
  `WM_DELETE_WINDOW` — 0 вхождений при 11 `root.after(`): `Сбросить` в паузе на старых экранах
  по-прежнему даст счёт `1 : 0`, то есть новый экран и старые будут вести себя по-разному. Это
  принятое расхождение (см. §Decisions Made). *Владелец: Human; триггер устранения — отдельная
  спека на выравнивание поведения «Сбросить» во всех экранах, по образцу задачи на баг операндов.*
- **Дедупликация окон при двойном клике по кнопке дашборда:** штатно открываются два наложенных
  окна `500x700` с раздельным счётом — унаследованное поведение Deduction-экранов, в этой задаче не
  правится.
- **Контраст служебных цветов во всём приложении:** `fg='green'` на `bg='lightblue'` — 1.11:1,
  `fg='red'` — 2.62:1, порог WCAG для крупного текста 3:1. Касается всех десяти экранов, правится
  одной общей задачей, а не внутри этой фичи. *(владелец: не назначен)*
- **Подсветка правильной кнопки после ответа** (визуальная, помимо текстового сообщения) — решение
  пользователя: согласованность с девятью существующими экранами важнее.
- **Рефакторинг пяти экранов старого паттерна** (`Deduction1020Screen`, `AdditionScreen`,
  `RandomWithin10Screen`, `RandomVia10Screen`, `DeductionScreen`) под новый паттерн: 8 кнопок,
  пауза 1000 мс, один общий label статистики, блокировка после проверки остаются как есть.
- **Извлечение базового класса `QuizScreen`** (общий UI, тайминги, блокировка, `finish_turn`,
  статистика). Порог извлечения: следующее ПАРАМЕТРИЗОВАННОЕ семейство экранов (деление,
  «Умножение» с настройками), то есть 11-12-й экран, а не одиночный новый. Сейчас не извлекать —
  дублирование структуры принято осознанно.
- **Сквозная локализация служебных строк** (`Back`, `Correct!…`, `Incorrect…`, `Correct: n`) —
  общеприложенческая задача, внутри одного экрана делать нельзя.
- **Любая тестовая инфраструктура:** `pytest`/`unittest`, линтеры, `requirements.txt`,
  CI-конфигурация, выделение генератора в отдельный тестируемый модуль. Скрипты V1/V2 транзиентны.
- **`.gitignore` и гигиена untracked-файлов** (`.idea/`): предусловие приёмки (Prereq-3), но не
  предмет этой спеки.
- **Прокрутка дашборда главного экрана:** сетка растёт только до 1024×768 по AC-1; скроллбар или
  `Canvas`-обёртка не добавляются.
- **Второй множитель `b = 1` и `b = 10`:** столбик сужен до 2..9 осознанно (требование
  пользователя), расширение диапазона — отдельное решение.
- **Структура сессии:** вопросы бесконечны, итогового экрана, цели и прогресса нет — наследование
  паттерна девяти существующих экранов.
- **Смешанный экран «Умножение: всё подряд»** (случайный первый множитель), настройки экрана
  (диапазон `b`, число вариантов, длительность паузы), сохранение статистики между запусками,
  деление и дроби.
